## 2. 覆盖判定：「完整题稿核验」到底覆盖了什么

**先说结论：A3/A4 只覆盖 10 个核验面里的 1 个（`answer`）。**

全仓的核验面由 `schema::recognition_v1::DecisionFieldV1` 定义，共 10 个：

| # | 字段 | 决定什么 | A3（原文件核验） | A4（分歧裁决） |
|---|---|---|---|---|
| 1 | `answer` | 答案 | **已实施**（答案层；模型只补确定性抽不到的槽位） | **已实施**（文本版；仅 `Answer` 字段） |
| 2 | `prompt` | 题干 / 指令文本 | 未覆盖 | 未覆盖（判据排除非答案字段） |
| 3 | `options` | 单题选项 | 未覆盖 | 未覆盖 |
| 4 | `option_bank` | 题组选项库 | 未覆盖 | 未覆盖 |
| 5 | `slot_interaction` | 填空 / 选择交互语义 | 未覆盖 | 未覆盖 |
| 6 | `group_kind` | 题组题型 | 未覆盖 | 未覆盖 |
| 7 | `slot_placement` | 答案位归属题组 | 未覆盖 | 未覆盖 |
| 8 | `asset` | 图 / 表等资源 | 未覆盖 | 未覆盖 |
| 9 | `source_coverage` | 原文覆盖（是否漏题） | 未覆盖 | 未覆盖 |
| 10 | `slot_participation` | 是否计分 | 未覆盖 | 未覆盖 |

**为什么刻意只做 `answer`**：其余 9 个字段的单方面替换会改写题稿结构（rich content、选项库、
题组划分、资源引用），而权威稿的写入路径（`apply_editor_commands_tx_with`）要求提交的
patch 在**合并后**仍通过同一套 `validate_authoring` 校验。让模型产出这 9 类 patch，等于把
「结构合法性」的举证责任从确定性校验转移到一个概率性组件上——这与本仓库
「本地稿权威、云端只读核验」的一贯边界相反。**这是一个设计取舍，不是遗漏**；
若要推进，应当先为对应字段定义「模型只能选择、不能发明」的可校验形态（同§3.3）。

> 说明：用户指令中的「八要素」在仓库内没有可检索的对应物（全仓 `要素` 零命中，
> 排除 `node_modules` 与 TypeScript 诊断词表）。上表用代码里真实存在的 10 个
> `DecisionFieldV1` 作为覆盖轴。**若你指的是另一份清单，请指认，我再按它重算覆盖。**

### 2.1 前三缺口（按风险排序）

1. **`source_coverage` 无模型参与（最高）**：云端可用时，`compare_slot_coverage` 只能发现
   「本地有、云端缺」；而**云端与本地都漏掉同一道题**时，没有任何一路能发现。
   这正是「完整题稿核验」最该回答的问题，而当前 A3/A4 都不碰它。
2. **`prompt` / `options` / `option_bank` 只有分歧没有裁决**：`PROMPT_CONFLICT` /
   `OPTION_BANK_CONFLICT` 一律 `NeedsReview` 且**不携带 patch**（单方面替换会破坏结构），
   用户只能手抄。风险不在数据错误，而在**这类项在长卷子里占比高、摩擦大**。
3. **`answer` 的证据面已接模型，但仍受两条限制**：A3 之后，`verify_against_source` 在
   确定性抽取判不了的槽位上会调用模型回原文件查值（PDF 直接附原文件，**扫描版答案页因此可读**）。
   仍然受限的是：① **本地没有值的槽位不送模型**——模型只做「核对已有值」，不做「发明新答案」，
   所以「本地与云端都空、只有原文有值」这类题仍需人来补；② 非 PDF 且抽不出原文文本时，
   网关侧 `source_verification_no_evidence_surface` 如实失败，不做空证据核验。

## 3. 已实施：A4 分歧裁决（+ 前置的形状对齐内核）

### 3.1 谁会进模型（判据）

`adjudicate.rs::needs_adjudication`，四条同时成立：

1. **云端链可用**（`Succeeded` / `Partial`）——云端没跑时没有可裁决的对手方；
2. 字段是 `Answer`——见§2 的理由；
3. 不是 `USER_EDITED`、不是 `DEPENDENCY_BLOCKED`——这两类是确定性规则的结论，不该被模型翻案；
4. 三条链**在答案层面确实不一致**（`has_answer_divergence`）：只看**确实给出了值**的链
   （`None` = 该链没有结论），但**空答案算一种取值**，因此
   `{local: 空, cloud: "stencilling"}` 是分歧，而 `{local: x, cloud: x, source: 无}` 不是。
   比较用 `answer_compare_key`，所以形状不同但值相同的答案**不会**被算成分歧。

判据**不看 `code`**（规则码是前端契约词表，用它做控制流等于把展示层当逻辑层）。

### 3.2 请求与预算

- **按批打包**：一次请求带上当批全部分歧项（`{decisionId, targetId, taskId, questionNumber, field, local, cloud, source}`）。
  按项调用会让「预算 2」在 8 处分歧时超支 4 倍。
- **单批软上限 12 项**（`ADJUDICATION_BATCH_SOFT_LIMIT`）：超出部分**留在待确认**并带
  `ADJUDICATION_BUDGET_EXHAUSTED`，不静默丢弃、不静默超支。
- **调用次数上限** `MAX_ADJUDICATION_MODEL_CALLS = 2`（1 次主裁决 + 1 次受约束修复），
  由调度器闭包里的 `Cell<u32>` 持有。第一次被拒时把**校验器的原话**回给模型再问一次
  （`repairNote`）；不带原因地重试只会拿到同一种错误，那是多烧配额而不是修复。
- 预算耗尽与「调用过但失败」用**枚举** `ModelCallFailure::{BudgetExhausted, Model(String)}`
  区分，而不是错误字符串——否则迟早有人写 `contains("timeout")` 去区分两者。
  （该枚举原名 `AdjudicationFailure`，A3 落地时改为两个通道共用的名字：核验与裁决的
  失败语义完全同构，各造一套只会让人分不清是谁失败的。）
- **预算按通道各持一份**（调度器里两个独立 `Cell<u32>`，共用同一段 `model_channel_call` 策略）：
  核验在裁决**之前**跑，两者共用一份额度会让核验吃光裁决的份额——那不是「有界」，
  那是裁决通道在真实生产路径上静默失效，而测试因为直接注入桩函数根本发现不了。
  单次导入的真实上限因此是 `2 × 2 = 4` 次模型调用（见 `MAX_ADJUDICATION_MODEL_CALLS` 的新注释）。

### 3.3 硬规则：模型只能「选择」，不能「发明」

`apply_ruling` 只接受**裁决值与所选链的值逐键一致**（经 `align_answer_value` 对齐形状之后）的裁定。
不一致 → 带 `ADJUDICATION_VALUE_NOT_CORROBORATED` 留在待确认，**不采纳为建议**。
模型因此无法引入第四条路，也无法借「置信度 0.99」蒙过一道闸。

### 3.4 如实上报（本次交付的核心语义）

| 情形 | 决策项 | `chains.adjudication` |
|---|---|---|
| 没有分歧项 | **完全不碰** | `Succeeded`（确定性裁决确实跑完了） |
| 有分歧，但**没有模型可用**（`adjudicator = None`） | **完全不碰**（逐项保持确定性规则的结论） | `NotRun` + `ADJUDICATION_MODEL_UNAVAILABLE` |
| 预算耗尽 | 各项带 `ADJUDICATION_BUDGET_EXHAUSTED`，resolution 必为 `NeedsReview`/`Unverifiable` | `NotRun` + 同码 |
| 调用超时 / 非法输出 / 不支持输入 | 复用 `classify_cloud_error` 的分类结果 | `Unusable` / `NotRun` + 对应码 |
| 模型明示无法裁定 / 漏答某项 | `ADJUDICATION_DECLINED`，resolution 不变 | `Partial` + `ADJUDICATION_DECLINED` |
| 裁定全部落实 | 项带具体建议 + 裁定留痕 | `Succeeded` |

**「没有模型可用时不碰项」是刻意的**：若顺手把每一项的 `reason_code` 改写成
`ADJUDICATION_MODEL_UNAVAILABLE`，未配置模型的用户就会看到满屏「模型未参与裁决」，
而真正的分歧原因（实质分歧 / 缺证据）反而消失了。

### 3.5 裁定留痕的形态

不新增 schema 字段，复用 `DecisionEvidenceV1`：

- `anchor_kind = "adjudication_ruling"`、`chain` = 被选中的那条链
  （这不是谎报：裁定说的正是「原文/云端/本地这一路是对的」）；
- `quote` = 模型的 `rationale`；
- `anchor` = `{chosen, corroborated, confidence}`。

这样 `DecisionItemV1` 的结构体字面量构造点（全仓 20+ 处）无需改动，
前端也能从现成的 `evidence` 数组里读到裁定。

### 3.6 与设计稿的一处**有意偏离**（需要你确认）

设计稿写的是「裁决会改写 `proposed_patch`，只有先裁决才能让原本待确认的项变成**可自动应用**
——这正是 A4 的产品价值所在」。

**本次实施没有让模型裁定解锁自动应用。** 理由：

- `adjudicate.rs` 的模块级硬约束是「自动应用**不依赖模型置信度**，只依赖确定性条件」；
  `task_plan.md` 的 AI 交互边界是「AI 的文字/答案/结构变更先作为候选 diff 展示，
  用户接受后才写入权威稿」。让一次模型回复直接授权改稿，会同时推翻这两条。
- A4 的实际交付改为：给分歧项一条**具体、带理由、一键可接受**的建议，并把
  `Unverifiable` 的项提升为 `NeedsReview`（契约规定 `Unverifiable` 不得携带 patch，
  而带 patch 的待确认项对用户就是一次点击）。「用户只处理少量疑问」的目标由
  **建议质量**达成，而不是由**免确认写入**达成。

若你要的是前者，改动是**一处**：在 `auto_apply_eligible` 的第 3 条守卫里，
把「建议值必须等于原文断言」放宽为「或等于一条已核实的模型裁定值」。
`ADJUDICATION_VALUE_NOT_CORROBORATED` 已经保证裁定值必然来自某条链，
所以这个放宽在数据上是自洽的——它是一个**产品决策**，不是技术障碍。

## 4. 前置重构（Step 0，已实施）

`candidate::align_answer_value(value, target_shape, bank) -> Option<Value>`：
把「**按目标形状重编码一个已有答案**」抽成唯一实现。`align_cloud_answer_shapes` 与
A4 的 `rulings[].value` 两处共用，**不允许各自再写一份**——
`answer_compare_key` 是形状敏感的，形状口径一旦分叉就会在**每一道题**上制造假分歧。

返回 `None` 的两种情形都表示「不要改写」：形状已一致；或不存在合法映射
（如选项任务里云端报的是选项文本、本地却没有可解析的选项库）。
后者必须让真实分歧上浮，绝不强行 unification。

> **A3 的实际情况（与设计稿不同，照实记录）**：A3 **没有**调用 `align_answer_value`。
> 模型核验的 `observedValue` 走的是 `source.rs::suggested_in_local_shape(local_kind,
> observed_text, assignment)` —— 与**确定性答案行抽取共用同一个形状内核**。
> 这样做的理由与本文其它取舍一致：确定性抽取与模型结论必须产出**同一种形状**，
> 否则同一个「原文给出的值」会因为来源不同而得出两种形状，进而制造假分歧。
> 代价（真实限制，见§5.4）：模型若回报选项**文本**而本地是选项题，本路径不去查选项库，
> 直接放弃建议（返回 `None`），不会把选项文本硬塞成标签。

## 5. 已实施：A3 原文件核验

### 5.1 与设计稿的三处偏离（都是为了收紧边界）

| 设计稿写法 | 实际实现 | 理由 |
|---|---|---|
| `SourceVerifyRunner = &dyn Fn(Option<&Value>, &[(String, u32, Option<Value>, bool, String)]) -> CommandResult<Value>` | `&dyn Fn(&[Value]) -> Result<Value, ModelCallFailure>` | 与 `adjudicator` 同一约定：**边界上是 JSON**，解析与契约校验留在网关侧，判定层只消费已验证结构。另外 `CommandResult` 会把失败压成字符串，而「预算耗尽（没尝试）」与「调用过但失败」必须可区分——它们的用户解释完全不同。 |
| 把 `document_ir` 传给 runner | **刻意不传** | 模型要看的必须是**原文件本身**（PDF 附件或独立抽取的原文文本）。把本地识别产物递进去，等于给了一条「拿本地识别结果当原文证据」的捷径，而那正是「把没验证写成已验证」的入口。 |
| 模型结论作为**追加证据**合并 | 只在槽位仍是 `NotVerifiable` 时合并 | 「追加」会允许一次模型回复推翻已成立的确定性结论（例如原文里明明可读的 `14 stencilling`）。核验的价值在补缺口，不在翻案。 |

落点：`engine.rs`（`SourceVerifyRunner` / `ReconcileBatchInput.source_verifier` / `source_stage_status`）、
`source.rs`（`verify_against_source` 第四参 + `merge_model_verification` + `model_evidence` +
`SourceModelStatusV1` + `SourceFindingV1::deterministic`）、
`llm_gateway.rs`（`verify_source_answers` 分支 + `source_verification_prompt` +
`validate_source_verification_output`）、`llm_suggestions.rs`（`make_source_verification_input`）、
`auto_pipeline.rs`（`verify_source_answers_through_gateway`）、
`processing/scheduler.rs`（生产接线 + 核验通道独立预算）、
`commands.rs`（`run_recognition_cycle_core_with_channels`）。

### 5.2 硬规则：模型只能「核对」，既不能「发明」也不能「翻案」

1. **只送确定性判不了的槽位**：`merge_model_verification` 的 `pending` 只收
   `verdict == NotVerifiable` **且本地确有值**的槽位。确定性已成立时模型**根本不被调用**
   （`model_verification_cannot_override_a_deterministic_conclusion` 直接断言调用次数为 0）。
2. **模型通道没有 `suggested` 结论，只有 `confirmed` / `contradicted`**：本地没有值的槽位要的是
   「给出一个全新答案」，那属于模型发明答案，本方案不做。
3. **每条断言必须有出处**：非空 `quote` + 1-based `pageIndex`。缺一不采纳
   （网关整份拒绝；`verify_against_source` 侧用 `model_evidence` 再拦一次，
   因为它也能被测试或其它调用方直接调用）。
4. **模型建议不解锁自动写入**：`SourceFindingV1::deterministic` 标记结论来源，
   自动应用守卫改读 `SourceVerificationV1::deterministic_suggested`（`adjudicate.rs::auto_apply_eligible`
   第 3 条守卫）。用户仍能看到模型建议并一键接受——差别只在**谁来敲下这一下**。
5. **与本地同形同值 ⇒ 不产生分歧**：模型报的值先经 `suggested_in_local_shape` 转成本地形状，
   再用 `answer_compare_key` 比对；相同就不虚构一条分歧。

### 5.3 如实上报（`chains.source` 的语义）

| 情形 | 决策项 | `chains.source` |
|---|---|---|
| 本批没有答案槽位 | 不碰 | `NotRun` |
| 确定性核验全部确认 | 不碰 | `Succeeded` |
| 部分确认（含模型补上的） | 不碰 | `Partial` |
| 原文读不出文本、模型也没给出结论 | 不碰 | `NotRun` + `SOURCE_FILE_UNREADABLE` / `EVIDENCE_MISSING` |
| 模型调用失败（超时 / 非法输出 / 不支持输入） | 不碰 | `Partial` + `classify_cloud_error` 的分类码 |
| 模型预算耗尽 | 不碰 | `Partial` + `SOURCE_VERIFY_BUDGET_EXHAUSTED` |
| 没有模型可用（未配 profile / 通道缺席） | 不碰 | 与未接入 A3 时**逐字一致**，不改写原因码 |

三条不变式：

- **状态在模型结论合并之后重算**（`slot_answer_counts`）：模型把某些槽位从「无法判断」
  提升为「已确认」后，链状态必须跟着变，否则会出现「结论变强了、状态还说没有证据」。
- **`model_status` 是独立字段**（`NotRun` / `Succeeded` / `Unusable` / `BudgetExhausted`），
  不靠链 `status` 反推；`BudgetExhausted` 与 `Unusable` 必须分得开。
- **没配模型的用户不会被刷屏**：缺席通道不写「模型未参与核验」之类的原因码——
  真正的原因（原文没有可核验的证据）反而会被顶掉。

### 5.4 仍然存在的限制（照实声明）

- **非 PDF 且抽不出原文文本** ⇒ 网关返回 `source_verification_no_evidence_surface`，
  如实失败而非静默降级。
- **本地无值的槽位不经模型**（§5.2 规则 2）：「本地和云端都空、只有原文有值」这类题仍需人补。
- **模型报选项文本时不查选项库**（见§4 末尾的说明）：形状映射不出字母标签就放弃建议。
- 模型只在**答案层**参与，10 个核验面里仍是 1 个（§2）。
- 真实模型的行为差异（幻觉、拒答、格式漂移）**未被任何测试覆盖**（§6）。

### 6.1 前端必须同步的四件事

1. **`chains.adjudication` 不再是恒定的 `succeeded`**（A4）：会出现 `not_run`（无模型可用）
   与 `partial`（部分分歧未获裁定）。既有教训：链状态覆盖不全曾把状态渲染成英文原文。
2. **新增 4 个 `reasonCode`**（A4）：`ADJUDICATION_BUDGET_EXHAUSTED`、`ADJUDICATION_DECLINED`、
   `ADJUDICATION_MODEL_UNAVAILABLE`、`ADJUDICATION_VALUE_NOT_CORROBORATED`。
3. **`chains.source` 不再是「`succeeded` / `not_run`」二分**（A3）：模型通道失败时是
   `partial` + 模型失败码（`MODEL_TIMEOUT` / `MODEL_INVALID_OUTPUT` 等，复用云端错误分类）。
   未配 profile 时**行为与从前逐字一致**（不会出现「模型未参与核验」刷屏）。
4. **新增 1 个 `reasonCode`**（A3）：`SOURCE_VERIFY_BUDGET_EXHAUSTED`。与
   `ADJUDICATION_BUDGET_EXHAUSTED` **刻意分开**：两个通道各自独立失败（核验跑通而裁决被拒
   是正常组合），合用一个码会让上游分不清是谁没有跑。

> **展示 vs 控制的边界**：下面两个字段是**诊断信息**，只可用于展示，不可拿来做控制流或
> 直接当用户文案（本仓库既有约定：reason code 与内部诊断不充当用户可见文本）：
> - `DecisionItemV1.evidence[].anchor.origin == "model"`；
> - `anchor_kind ∈ {model_quote, model_quote_question_token_absent}`。
>
> 「这一项能否自动写入」的唯一判据是后端已经算好的 `auto_apply_candidates` /
> resolution，前端不要自己按 `anchor_kind` 字符串推断。
