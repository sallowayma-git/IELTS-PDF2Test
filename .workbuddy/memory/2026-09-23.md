## 本机环境的关键发现（重要，别再踩）

**「WebView2 CDP 在本机不可用」是误判**，两层原因叠加：

1. **交给 App 的子进程环境被污染** → DevTools 端点根本起不来。
   修法：`tauri-cdp-harness.mjs::sanitizedAppEnv()` 清掉 `HTTP(S)_PROXY`/`ALL_PROXY`、
   `__COMPAT_LAYER`、`PATH` 里空项与不存在的目录。
2. **本沙箱下 WebView2 renderer 需要 `--no-sandbox --disable-gpu`**，否则启动约 7s 后
   renderer 崩掉：**DevTools HTTP 端点消失、App 进程仍然活着**。
   - `tauri-cdp-smoke.mjs` 的**默认值**就是这两个开关，注释里写着「环境必需」。
   - `tauri-cdp-single-file-import.mjs` 默认**不带**（`cdp-default`），所以在诊断档才跑得通。
   - 带诊断参数的运行记 `runProfile=cdp-diagnostic`，**不得**写成「默认产品路径通过」。
   - 诊断手法：`tmp/probe-app-exit.mjs`（只 spawn exe + HTTP `/json/list` 轮询，**不建 WebSocket**），
     带/不带 `PDF2TEST_AUTOMATION_SOURCE_FILES` 两次对照逐行同形 → 排除该变量是诱因。
   - 另一个坑：WebView2 会**重建 page target**，旧 WebSocket 随之关闭。
     `TauriCdpSession` 现在会 `attachToPageTarget()` 重新附着（`evaluate` 里自动重试一次），
     否则报错会伪装成「页面 90s 内未渲染出可见文本」，把人往「前端没渲染」方向带偏。

## R2（学生端仓库 `IELTS-NASfor-WenDao-listening`，分支 `feat-listening-per-part-media`）

缺陷：`NasJsDirectReadingAssetProvider.listAssets()` 只比 `schemaVersion`，**不看 `modality`**；
`ListeningExamSourceV1` 恰好「不等于阅读 V2 版本」→ 被放行 → 听力卷出现在阅读目录。

修法：`isReadingEntry(entry)`（modality 优先否 → 无 schemaVersion 视为阅读 → 否则阅读 schema 白名单）；
